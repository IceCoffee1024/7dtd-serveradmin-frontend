# 游戏物品与方块

> 面向有游戏物品查询权限、并在需要时具备玩家管理/发放物品权限的管理员。需要后端可达并已加载游戏物品目录；发放还要求目标在线，并会产生审计记录。

## 目的

在商店、奖励、命令或玩家发放前找到准确的 7 Days to Die 内部物品或方块标识，再通过玩家库存和审计记录验证发放结果。

## 开始前

- 确认 **游戏物品** 能加载当前目录，并在[玩家列表与隐藏的玩家画像](../daily-operations/players)中核对目标玩家的稳定 Player ID。
- 先判断需要的是物品还是方块。数量不要超过页面显示的最大堆叠，并准备符合服务器规则的品质/模组方案。
- 获取发放权限并确定要保存审计记录的位置，再执行线上变更。

## 操作步骤

### 安全查询

1. 打开 **游戏物品**，按内部名称或本地化名称搜索，并在 **全部**、**物品**、**方块**之间切换。只有确有需要检查通常隐藏的条目时才开启 **显示用户隐藏**。
2. 悬停匹配条目，对比内部名称、本地化名称、物品/方块标签、最大堆叠和图标颜色。用右键菜单复制内部名称，并保留原有大小写。

### 发放与核验

3. 打开目标玩家画像或库存发放对话框，再次确认稳定 Player ID 和在线状态，选择复制的物品名称，填写数量、品质和允许的模组；提交前阅读确认文本。
4. 发放成功后重新加载玩家当前库存，或从追踪功能生成一次库存快照。将物品名、数量、品质和模组与请求对照，然后打开对应审计条目，记录操作员、目标、结果和时间。

## 验证结果

- 目录结果显示预期的内部名称和物品/方块类型，没有误用相似名称。
- 玩家当前库存或快照包含请求的堆叠，发放响应或提示显示成功。
- 审计行包含操作员、目标 Player ID、物品载荷、结果和时间；失败或部分成功必须先调查再重试。

## 限制与安全说明

::: warning
目录查询是只读的，但发放会改变玩家状态。不要从显示名称推断物品 ID，也不要在未测试的情况下发放方块或只由模组提供的标识；游戏更新或不支持的模组可能改变目录。
:::

::: danger
发放物品会影响进度，移除一个堆叠也不一定能撤销全部影响。使用最小数量，保留确认文本和审计记录，截图或工单中不得公开 Player ID 和库存内容。
:::

- 库存发生变化本身不是审计轨迹。将发放响应当作结果核验，将审计行作为操作员/动作边界。
- 查询页面不能证明命令、商店或奖励包一定能交付该物品；还要验证后端接受标识，并确认目标库存实际收到物品。
